# 精度经验及证明边界

来源为当前对话及工作区保存的验证记录。不要把“用户报告”“主机复核”“Docker 原生”和“板端”合并成一个已验证标签。

| 结果/观察 | 来源层级 | 可以得出的结论 |
|---|---|---|
| 原前端 CLE DPU + FP32 PS 后端，255/300，85% | 用户板端 summary | 有可比较的部署基线；不是普通 SO→CLE 的提升对照 |
| 两个额外 MV2 使用 CLE 后三段 DPU，237/300，79% | 用户板端 summary | 多段 INT8 引入额外误差，需要逐段定位 |
| 两个 MV2 只 BN 折叠时 28% | 用户反馈；本对话未附该轮全量报告 | BN-only 不一定更好，应作为对照；不能把下降简单归因某一个参数 |
| MV2_4 首层最大偏置约 9.92→268.98，量化步长为 2 | 参数/量化图观察 | 有理由同时看偏置、激活与权重；这是线索，不是单独确认根因 |
| `control` 240/300；`c08` 221；`c32` 234；`c128` 240；`control_bc050` 249；`control_bc100` 250 | 用户贴出的相同口径原生比较 | 第一个 MV2 的偏置校正候选增加 10 张，较对照约 +3.33 个百分点；不是实板已达到 83.33% |
| 上述实验固定前端和 MV2_5，修改 MV2_4 | 该轮脚本和选择输出 | 该收益不能说成“固定两个 MV2 后，前端 CLE 已提升” |
| 前端基础候选 300 张 FP32 误差不超过约 3.48e-4、relative L2 不超过约 1.36e-6 | 本机前端验证记录 | 基础浮点变换足够接近；尚不能证明新整体 INT8 提升 |
| 用户报告全 FP32 约 91.3%，本机 TF 解码参考 275/300=91.67% | 不同输入执行流程 | 要重算同口径基线并对齐 decoder，不能直接拿百分比相减归因 |
| 前端优化范围最终确认为“两个已有优化 MV2 固定在 DPU” | 用户需求纠正与更新脚本 | 最终候选必须由完整三段链路选，子段诊断分数不能代替主指标 |
| 旧 Runtime Python 在新输出目录 `.resolve()` 失败 | 用户堆栈；主机严格路径语义回归 | 图精度问题与打包路径问题分开处理，重跑链接组装可复用未变 ELF/SO |

给陌生队伍的迁移方式：保留“按真实完整链路评分、冻结其他阶段、实数范围与元数据对应、原生/实板分层证明”的原则；重新推导自己的 cut、shape、scale、候选、阈值、架构和编译命令。案例的 kernel、5/0 位置、300 张、10 类均不是通用要求。

本包新的通用脚本测试结果在 `skill/validation/`。固定案例最终 SO 的工程交付或文件存在本身，不能补成缺失的板端精度测量。
