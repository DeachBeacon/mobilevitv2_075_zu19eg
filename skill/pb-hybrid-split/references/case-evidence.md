# 本技能从哪些观察中提炼

来源 A：用户提供的 Markdown《排查 VAI 编译 Transpose 报错》（随提交包记录源文本 SHA256，不复制账号路径和长工具日志）。来源 B：本聊天的 MobileViTv2 分段与部署历史。新工具的本次测试另见 `skill/validation/`。

| 观察/结果 | 证据层级 | 提炼出的可复用规则 |
|---|---|---|
| 原量化 deploy 图 30 个 Transpose 的 perm 仍为独立 Const | A 的静态检查，报错未给具体首个节点 | 量化成功不等于编译支持；看真实工具和图语义，不删 Const 糊过去 |
| 6 处 Reshape 属性与源图实际形状不同；首例 [32,16,2,96] 与 [1,16,2,96] | A 的图/属性检查；旧编译器解释尚未验证 | 对元素数/布局做黄金验证，不能仅消除报错 |
| 前段 CNN / 后段 PS 两段在 10 张实际图片 logits 误差为 0 | A 的主机 FP32 保存 PB 串联验证 | 每段保存后重新读取验证，不以成功导出作为证明 |
| 同批 NumPy 后端最大 logits 误差约 3.82e-6，类别一致；阻断 TF 导入仍可自检 | A 的主机 CPU 后端验证，NumPy 1.19.5 | 无 TF 的 ARM 需要真正可执行 CPU 后端；API 兼容不等于已完成 ARM 实测 |
| 初期七段方案 3 图浮点误差 0 | A 的小样本静态/主机验证；未证明该方案编译与速度 | 这是可切分证据，不是最佳分工或实板性能证据 |
| 后来拆出两个 MV2 进入 DPU，板端原 CLE 组合为 237/300 | B 的用户板端反馈 | 继续测量化精度与往返开销；FP32 等价不是 INT8 等价 |
| `driver` 目录曾被错误建议删除，用户容器 ls 证实真实位置包含它 | A 的路径排查 | 以当前出错环境的文件为准，不把本机目录层级当作容器事实 |
| 用户明确希望两个 MV2 继续 DPU，曾被误理解为回到 PS | B 的需求纠正 | 把最终后端分工写入实验契约，防止优化时改变问题 |

案例切点 `stack3_block2_pre_2_conv/Conv2D:0` 和 `[1,32,32,96]` 只供理解案例；辅助脚本没有它们的默认值。早期七段与后来六段方案边界不同，不能混用通道数或 runtime 节点。

本包对不同模型的可复用性以新生成的合成残差/多端口测试与可选真实案例复核为证据；没有声称覆盖任意算子、PYNQ 硬件或所有 TF 版本。
