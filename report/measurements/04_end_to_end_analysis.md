# 提速效果分析与下一步（2026-10-31）

> 性能口径：完整基线从 **33.0 s**（未切分、未优化纯 PS）开始；本文的 19 s 是“切一刀后、仍无 BLAS”的中间点，0.745 s 是加 OpenBLAS 后，最终 0.527 s（87.00%）。


板端实测（队友回传 `summary(3).json` / `predictions(2).csv`）：
kernel `mobilevitv2_075_front_cle`（CLE 前段）、后段 `ps_tail_numpy`（**未加 `--fast-tail`**）、
300 张 test1_p、warmup 1。

---

## 1. 性能：19 s → 0.745 s，25.5×

| 指标 | 旧 | 新 | 变化 |
| --- | ---: | ---: | ---: |
| 端到端单张 | ≈ 19 s | **0.7454 s** | **25.5×** |
| 吞吐 | ≈ 0.05 张/s | **1.34 张/s** | 25.5× |
| 300 张总时间 | ≈ 95 min | **224 s（3.7 min）** | 25.5× |

### 1.1 时间去哪了（300 张平均）

| 段 | 秒/张 | 占比 |
| --- | ---: | ---: |
| 预处理 | 0.0414 | 5.6% |
| DPU 前段 + 传输 | 0.0125 | 1.7% |
| **NumPy 后段** | **0.6891** | **92.4%** |
| 合计 | 0.7454 | 100% |

结论很清楚：**瓶颈仍然在后段（92%）**，DPU 只占 1.7%。所以：

- 做任何“DPU 侧”的改动（比如把分类头搬进 DPU，只占 0.2%）对总时间没有意义；
- 要再快，只能压后段（0.689 s）或改后段执行方式。

### 1.2 为什么这次能快 25 倍

1. NumPy 1.17 → **1.19.5 + OpenBLAS**（matmul 9.37 GFLOP/s），后段从 19 s 量级降到 0.69 s；
2. 前段仍是 DPU（CLE 版本），只花 12.5 ms；
3. 这次**没有**用 `--fast-tail`，所以还有一步“免费加速”没吃到（见 3.1）。

---

## 2. 准确率：85%（255/300），比 FP32 低约 6.7 个点

| 类别 | 正确/总数 | 召回 | 被判成该类 | 精度 |
| --- | ---: | ---: | ---: | ---: |
| c0 | 32/33 | **97.0%** | 51 | **62.7%** |
| c1 | 26/30 | 86.7% | 27 | 96.3% |
| c2 | 25/31 | 80.6% | 25 | 100% |
| c3 | 31/31 | 100% | 31 | 100% |
| c4 | 27/31 | 87.1% | 27 | 100% |
| c5 | 23/30 | 76.7% | 23 | 100% |
| c6 | 27/31 | 87.1% | 28 | 96.4% |
| c7 | 24/27 | 88.9% | 35 | **68.6%** |
| c8 | 23/27 | 85.2% | 34 | **67.6%** |
| c9 | 17/29 | **58.6%** | 19 | 89.5% |

主要错分：`c9 → c0`（8 张）、`c2 → c8`（5 张）。

要点：

- **c0 被过度预测**：51 张被判成 c0，只有 32 张是真的，精度 62.7%；
  c9 有 8 张被吸到 c0，是掉点的主因。
- 工程里 FP32 参考是 **91.67%（275/300）**，当前 INT8 掉 20 张 ≈ **6.7 个点**。
- 这 300 张同时是校准集，所以 85% 已经是“偏乐观”的数字；真正的泛化集会更低。
- 32 张那次 29/32（90.6%）是小样本，不代表整体。

**这说明：速度已经达标，但精度还有 6–7 个点要补**，否则报告里“29/32”会被质疑（300 张只有 85%）。

---

## 3. 下一步优化（按性价比排序）

### 3.1 立刻：开 `--fast-tail`（免费，今天就能做）

这次批量用的是 `ps_tail_numpy`（`tail_impl` 字段可证），没有用快速后段。板上 A/B 已测：

```text
baseline 694.16 ms → fast 581.11 ms（1.19×），logits 差 3.1e-6
```

预期：`numpy_tail 0.689 → ≈0.577 s`，`total ≈0.631 s`，**相对 19 s 约 30×**。
模型、准确率完全不变（数值差 1e-6 级）。

```bash
python3 runtime/run_hybrid_batch.py \
  --kernel mobilevitv2_075_front_cle \
  --image-dir ./test1_p --labels-from-folders \
  --tail-graph baseline/model/ps_tail_numpy.json \
  --fast-tail --output-dir batch_cle_fast_300
```

### 3.2 之后：融合注意力与 GroupNorm（再 8–12%）

后段里除去卷积，最大一块是逐元素算子（板上 profile）：

| 算子组 | 时间 | 占后段 |
| --- | ---: | ---: |
| Conv2D + Depthwise | 266.5 ms | 43.9% |
| BN + BiasAdd + Identity | 134.9 ms | 22.2%（`--fast-tail` 已消掉大部分） |
| Mul + Mean + SquaredDifference + Sub + Sum + SplitV + Softmax + Rsqrt | 134.5 ms | 22.2% |
| Reshape + Transpose | 16.9 ms | 2.8% |

把 group-norm 与 attention 的 Mul/Sum 改成批量 matmul、原地归一化，预计再省 **60–90 ms**，
`total` 可到 **0.54–0.57 s（33–35×）**。数学等价，不改模型。

### 3.3 再切分：两个纯卷积块回 DPU（理论上限约 25%，不是 28%）

**先把账算清楚**（数据来自板上 profile，后段 606.6 ms）：

| 块 | 时间 | 占后段 | 能否进 DPU |
| --- | ---: | ---: | :---: |
| `stack4_block1` | 102.8 ms | 16.9% | 能（纯卷积） |
| `stack5_block1` | 65.2 ms | 10.7% | 能（纯卷积） |
| 两者合计 | **168.0 ms** | **27.7%** | — |

所以“28%”是**后段内部**的比例；换算到端到端（后段占 92.4%）：

```text
0.7454 s × (0.6891 - 0.168) / 0.6891 ≈ 0.563 s
```

也就是 **端到端约 −24.5%**（19 s 基线不变时，相当于 25.5× → 33.7×）。
这不是“空想”，但有三笔成本必须先算：

**① 工程成本**

- 现在的 `split_model.py` 只支持**单切点**，要改成“多切点 + 多段导出”；
- 两个新 DPU 段要各自**量化**：需要从浮点模型抓这两个段输入处的**中间特征**做校准
  （300 张 × 两次抓取），不是拿现有校准图直接喂；
- 各自 `2_compile_front.sh` / `3_link_front.sh`（两套 kernel 名）；
- 板端 runtime 从 2 段变成 **3 段串联**：DPU1 → PS1 → DPU2 → PS2 → DPU3 → PS3，
  节点名、计时口径、失败处理都要改；
- 估计 **3–5 天**（不含精度返工）。

**② 精度风险**

- 现在 INT8 已经比 FP32 低 6.7 个点；再加两个 INT8 边界（多两次量化/反量化），
  掉点风险是实打实的；每加一段都要重新验证 300 张。
- 建议**一次只加一个块**（先 `stack4_block1`，占 16.9%），验证精度和收益后再加第二个。

**③ 收益上限**

- 这两个块搬走后，后段剩 0.521 s（689−168），端到端 ≈0.575 s；
- 如果先做了 3.1、3.2（后段已到 ~0.51 s），再搬这两块，后段 ≈0.34 s，端到端 ≈0.40 s（47×）；
  但那是“叠加后”的理想值，实际要打折。

**可行性结论**：

- **技术可行**：两个块只有 Conv2D/Depthwise/BN/ReLU/Pad/Add，Vitis AI 1.2 支持；
- **收益真实但不是 28%**：端到端约 **20–25%**；
- **不建议作为下一步**：先做 3.1（免费）→ 3.2（1–2 天、等价）→ 再决定是否值得花 3–5 天做 3.3；
- 如果最终要做，**先加 `stack4_block1` 一块**，用 300 张验证精度掉点 <1 个点再继续。

### 3.4 备选：ONNX Runtime 跑后段

工程里有 `int8_best/model_int8_qdq.onnx`（4485 张 99.22%）。板上装 `onnxruntime` 后，
CPU EP 有 NEON 优化，后段有机会再快 2–4×，但那是换运行时、不走 DPU，属于另一条路线。

### 3.5 精度补回（与提速并行）

- 校准：确认 300 张是否覆盖 c9/c5 的分布；可试更大或更均衡的校准集；
- QAT：对 CLE 前段做几轮伪量化微调，最稳，但要训练环境；
- 分析 c0 偏置：看错分样本的 logits margin，判断是量化噪声还是模型本身偏置。

## 4. 建议的执行顺序

| 顺序 | 动作 | 预期端到端 | 工作量 | 风险 |
| --- | --- | ---: | --- | --- |
| 1 | 加 `--fast-tail` 重跑 300 张 | **≈0.63 s（30×）** | 10 分钟 | 无（diff 3e-6） |
| 2 | 注意力/GroupNorm 融合 | ≈0.54–0.57 s（33–35×） | 1–2 天 | 低（等价改写） |
| 3 | 精度：校准/QAT 把 85% 拉回 ~90% | 不变 | 2–5 天 | 中 |
| 4 | 再切分（先 stack4_block1，再 stack5_block1） | ≈0.42–0.55 s | 3–5 天 | 中高（精度） |
| 5 | ORT 评估 | 可能 <0.4 s | 1–2 天 | 中（换运行时） |

**回答“还能不能再快 28%”**：后段内部是 28%，端到端约 **20–25%**；技术上可行，
但要 3–5 天、多两套量化和精度验证，建议排在 1、2 之后，并且先做一块验证。

---

## 5. 这次结果怎么写进报告

- 速度：19 s → **0.745 s（25.5×）**；若加 `--fast-tail`，→ **≈0.63 s（30×）**；
- 分段：后段 92.4%、预处理 5.6%、DPU 1.7%，说明“瓶颈已从环境问题转为后段计算”；
- 准确率：300 张 **85%**（FP32 参考 91.67%），INT8 掉点约 6.7 个点，主要错分 `c9→c0`；
- 结论：NumPy/BLAS 是这次提速的主因；再切分只能再拿 20–25%，而精度风险更大，
  应优先做 `--fast-tail` 与后段算子融合。
